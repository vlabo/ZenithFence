## `sim/src/lib.rs`

`zfsim._native`: the real ZenithFence driver (over the mock WDK) loaded
in-process and driven from Python through plain function calls.
This crate is only the interface: scenarios, traffic, seeds and assertions
live in Python scripts. A [`Sim`] owns the one global driver and serves it on
the agent's named pipe / Unix socket (`serve()`); the agent is always a real
one connected there. The pumps tee the events the agent receives and the
commands it sends into queues the script reads.
Traffic is injected through the driver's callout entry points (`ale_connect`,
`packet`, ...), exactly like the OS would. The wire protocol never reaches
Python: events are decoded by `driver_harness::sim`.

## `sim/src/pipe/mod.rs`

The agent-facing endpoint, one implementation per OS behind the same
`PipeServer` API (`create`, `wait_for_client`, `write_all`, `read_message`,
`disconnect`). One client is served at a time; after `disconnect` the server
can `wait_for_client` again for the next one:
* Windows: an overlapped, message-mode named pipe (`\\.\pipe\<name>`).
* Unix: a stream Unix domain socket. Stream sockets don't preserve message
  boundaries, so on this transport the agent prefixes each command with a
  `u32` little-endian length, which restores "one command message = one
  `Device::write`". The event direction stays an unframed byte stream on both.
[`endpoint`] maps the logical name (`ZF_SIM_PIPE` on the Go side) to the OS
address. The Go side (`kext_interface/sim_conn*.go`) applies the same rule.

## `sim/src/pipe/unix.rs`

Unix domain socket server: the Unix counterpart of the Windows named pipe.
A `SOCK_STREAM` socket from `std` (no extra dependencies). Reads and writes
run on separate threads over separate fds (`try_clone`), the same concurrency
the overlapped pipe provides on Windows.
Stream sockets don't keep message boundaries, but the driver needs one command
per `Device::write` (one IRP per `WriteFile` in the kernel). So on this
transport each agent command arrives as a frame: a `u32` little-endian length,
then that many bytes. `SOCK_SEQPACKET` would keep the boundaries without
framing, but it truncates any message larger than the reader's buffer, and the
agent deliberately reads events through a small (1 KiB) buffer. Events are
therefore sent as a plain byte stream, exactly like the pipe's byte-mode reads.

## `sim/src/pipe/windows.rs`

Minimal Windows named-pipe server with overlapped (asynchronous) I/O.
Raw `kernel32` FFI (no `windows-sys`/`windows` dependency, so it is immune to
the version churn in those crates and pulls nothing extra into the build).
The handle **must** be overlapped: the daemon reads commands on one thread and
writes events on another, and on a *synchronous* pipe handle Windows
serializes all I/O — a blocked `ReadFile` (waiting for a command) would block
every concurrent `WriteFile` (sending an event), which deadlocks the pipeline
(no events out -> no verdicts in -> read never unblocks). With overlapped I/O
each operation carries its own OVERLAPPED + event and completes independently,
so reads and writes run concurrently.
The pipe is **message** type so each agent `WriteFile` (one per command)
arrives as a single message on our read side — one message maps to one
`Device::write`, exactly like one IRP per `WriteFile` in the kernel. The agent
reads events in byte mode (its default), so the byte-oriented event parser is
unaffected by message boundaries.

## `sim/src/pumps.rs`

Loading the driver and bridging it to an agent on the pipe.
[`Pumps`] are the two threads between the pipe and the driver's user-space
channel (events out, commands in). They can *tee* what flows through them
