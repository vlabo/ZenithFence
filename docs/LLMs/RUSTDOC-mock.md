## `mock/wdk/src/connection.rs`

Host-only user-space client for the mocked driver.
`DriverConnection` mirrors the Win32 device-handle API a real user-space
agent uses (`ReadFile` / `WriteFile` / `DeviceIoControl`): each call
synthesizes a mock `IRP` and invokes the dispatch handler the driver
registered in its `DRIVER_OBJECT`, exactly like the kernel I/O manager. This
is what lets the full-driver simulation talk to the driver "like a real
driver" instead of poking `Device` methods directly.
Each connection owns its own `DEVICE_OBJECT`, and the dispatch methods take
`&mut self`, so the `&mut DEVICE_OBJECT`/`&mut IRP` a handler receives are
never shared across threads — every thread (producer, consumer) opens its own
connection from the same `DRIVER_OBJECT`.

## `mock/wdk/src/driver.rs`

Host mock of `wdk::driver::Driver`.
In production this wraps the WDM `DRIVER_OBJECT`/`DEVICE_OBJECT` and registers
IRP dispatch handlers by writing function pointers into
`DRIVER_OBJECT.MajorFunction[IRP_MJ_*]`. The mock mirrors that exactly so the
real `DriverEntry` runs unchanged and a `DriverConnection` can read the
handlers back from the `DRIVER_OBJECT` and dispatch like the I/O manager.
`Driver::mock()` (carrying a null driver object) keeps the older
`Device::new(&Driver::mock())` fuzz/test path working: with no driver object,
the `set_*_fn` registrations are no-ops, which is fine because that path never
dispatches through the registered handlers. It does carry a (static, zero
sized) device object, because the mock filter engine — like the kernel's
`FwpsCalloutRegister` — refuses callout registration without one.

#### `IOQueue`

Host mock of the kernel `IOQueue`, backed by a `VecDeque` guarded by a
`Mutex` + `Condvar`.
The driver creates its queue with `IOQueue::new()` (the same call as against
the real `wdk`), so the mode is a process-wide setting the harness picks
before loading the driver ([`set_default_blocking`]). The host harness has
two very different needs:
* **non-blocking** — `wait_and_pop` returns `Timeout` immediately when
  the queue is empty. The synchronous fuzz targets drain the event queue on
  the same thread that drives the callouts, so a blocking read there would
  simply hang the fuzzer. This matches the real `pop()` (zero timeout).
* **blocking** (the default) — `wait_and_pop` blocks until an entry is
  pushed or the queue is run down, mirroring the kernel `KeRemoveQueue` with a
  NULL timeout. The full-driver simulation uses this so a user-space reader
  thread blocks on `Device::read` exactly like the real driver, and `rundown`
  (shutdown / unload) wakes it with `Abandoned`, which `Device::read` turns
  into a clean end-of-file.

```rust
pub struct IOQueue<T> {
    inner: Mutex<Inner<T>>,
    cond: Condvar,
    blocking: bool,
}
```

```rust
impl<T> IOQueue<T> {
    /// A queue in the mode chosen by [`set_default_blocking`] (see type docs).
    pub fn new() -> Self;
    fn with_blocking(blocking: bool) -> Self;
    pub fn push(&self, entry: T) -> Result<(), Status>;
    /// Non-blocking pop. Returns `Timeout` when empty (mirrors the real `pop()`
    /// with a zero timeout).
    pub fn pop(&self) -> Result<T, Status>;
    pub fn wait_and_pop(&self) -> Result<T, Status>;
    /// Blocks up to `timeout` milliseconds for an entry. Returns `Timeout` if the
    /// deadline passes with the queue still empty, or `Abandoned` after rundown.
    pub fn pop_timeout(&self, timeout: i64) -> Result<T, Status>;
    /// Closes the queue: drops all pending entries and wakes every blocked
    /// waiter with `Abandoned`. The queue must not be used afterwards (mirrors
    /// `KeRundownQueue`).
    pub fn rundown(&self);
}
```

## `mock/wdk/src/rw_spin_lock.rs`

### Types

#### `Mutex`

Host mock of the kernel reader-writer spin lock based `Mutex`.
This is a REAL reader-writer spinlock (not a no-op), so the multithreaded
host fuzz/stress harness exercises the same mutual exclusion the kernel
spinlock provides. Multiple readers may hold it at once; a writer is
exclusive.
IMPORTANT: the real type is valid when zero-initialized, and the driver
relies on that -- `connection_cache::alloc_port_array` allocates arrays of
`RCUPort<T>` (which contain `Mutex<()>`) with `alloc_zeroed`. So this mock
must also be valid when its bytes are all zero. We back the lock word with an
`AtomicIsize` that is `0` (unlocked) when zeroed:
  *  `0` -> unlocked
  * `-1` -> write-locked (exclusive)
  * `>0` -> number of active readers (shared)
The data lives in an `UnsafeCell<T>`; the lock word is what makes concurrent
access sound. No lock-ordering cycles exist in the driver (each operation
holds at most one port lock at a time), so this spinlock cannot deadlock.

```rust
pub struct Mutex<T> {
    lock: AtomicIsize,
    data: UnsafeCell<T>,
}
```

```rust
impl<T> Mutex<T> {
    pub const fn new(data: T) -> Self;
    /// Acquire a shared (reader) lock, spinning until no writer holds it.
    pub fn read_lock(&self) -> MutexReadGuard<'_, T>;
    /// Acquire the exclusive (writer) lock, spinning until fully unlocked.
    pub fn write_lock(&self) -> MutexWriteGuard<'_, T>;
}
```

## `mock/harness/src/lib.rs`

Host harness for the ZenithFence driver, used by the Python module `zfsim`
(sim/).
Everything here drives the REAL driver: `driver` is the `driver-mock`
package, which compiles the production sources in driver/src against the
host mock of the Windows kernel API (mock/wdk). The harness only uses the
driver's public API -- it loads it through `driver_entry`, calls its callout
entry points, talks to it through the user-space channel, and observes its
state -- so no test code lives in the driver itself.

## `mock/harness/src/loader.rs`

Loads and unloads the real driver the way the kernel does.
The driver keeps its device in a process-wide global, so there is one loaded
driver per process. Loading runs the real `driver_entry` against a fresh mock
`DRIVER_OBJECT`; unloading calls the `DriverUnload` that `driver_entry`
registered on it. Nothing here reaches into the driver's globals directly.

## `mock/harness/src/sim.rs`

The loaded driver and its user-space channel.
Loads the *real* driver via its `DriverEntry` (over the mocked WDK); the
agent side talks to it through the same channel a real agent uses
([`wdk::connection::DriverConnection`] = `ReadFile`/`WriteFile`/`DeviceIoControl`).
[`EventParser`] / [`Event::decode`] read the event stream it produces.
Teardown order is load-bearing: `shutdown` runs down the event queue so a
blocked reader wakes with end-of-file; join the readers; only then drop the
`Simulation`, which unloads the driver through its registered `DriverUnload`.

### Types

#### `Simulation`

A loaded driver instance (reads block, like a real user-space agent's).
Holds the harness driver lock
for its lifetime so concurrent tests don't fight over the one driver per
process, and unloads the driver when dropped.

```rust
pub struct Simulation {
    _guard: std::sync::MutexGuard<'static, ()>,
}
```

```rust
impl Simulation {
    /// Load the driver through its real `driver_entry`. A driver left loaded by
    /// an earlier harness user is unloaded first, so this run starts clean.
    pub fn start() -> Result<Self, NTSTATUS>;
    /// Open a fresh user-space connection to the driver. Each thread should use
    /// its own (the dispatch handlers take `&mut` device/IRP per call).
    pub fn connect(&self) -> DriverConnection;
    /// Request shutdown: resolve pending packets and run down the event queue so
    /// any blocked reader wakes with end-of-file. Idempotent; safe to call
    /// from any thread.
    pub fn shutdown(&self);
}
```
